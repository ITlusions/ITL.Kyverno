# 1.2 Deployment

**Status: scaffolded, not yet deployed.** Confirmed live 2026-10-29 (`kubectl get ns`, `helm list -A`, `kubectl get clusterpolicy` all checked against the `itl` cluster context): no `kyverno` namespace, no `ClusterPolicy` CRD, no matching Helm release anywhere. This repo exists and lints clean; nothing from it has been applied to the cluster yet.

## Deploy

```bash
cd itl.kyverno
helm dependency update
helm upgrade --install kyverno . -n kyverno --create-namespace
```

## Verify

```bash
kubectl get pods -n kyverno
kubectl get clusterpolicy
kubectl describe clusterpolicy spiffe-helper-nonroot
```

A pod containing a `spiffe-helper` container, created *after* this chart is installed, should show the patched `securityContext` (`runAsUser`/`runAsGroup` from `values.yaml`'s `policies.spiffeHelperNonRoot.uid`/`gid`) without any change to the chart that created that pod:

```bash
kubectl get pod <pod> -o jsonpath='{.spec.initContainers[?(@.name=="spiffe-helper")].securityContext}'
```

## Known gap: not yet tested against a real mutation

The policy (`itl.kyverno/templates/spiffe-helper-nonroot.yaml`) lints clean and renders the expected YAML (`helm template`), but **has not been exercised against a live admission request** - i.e., no pod with a `spiffe-helper` container has actually been created while this policy was installed and active. Before relying on it to replace the hand-patched fix already shipped in `ITL.Openproject.fork`'s own chart, redeploy that chart's `web`/`worker`/`cron` Deployments (or any pod with a `spiffe-helper` container) with this policy installed and confirm the patch actually lands - the JMESPath preconditions (`request.object.spec.initContainers[?name == 'spiffe-helper'] | length(@)`) are Kyverno's own templating syntax, escaped past Helm's own `{{ }}` templating with backtick raw-string literals in the chart source; a typo there would fail silently (the rule simply never fires) rather than loudly.
