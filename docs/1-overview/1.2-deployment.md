# 1.2 Deployment

**Status: deployed and verified live**, 2026-10-29, `kyverno` namespace on the `itl` cluster (Helm release `kyverno`, revision 7). All four controllers (admission, background, cleanup, reports) running; `spiffe-helper-nonroot` is `Ready`.

## Deploy: two-step, first install only

Kyverno's own CRDs (`ClusterPolicy` etc.) and this repo's own `ClusterPolicy` resource are both part of the same Helm release, so a first install fails: Helm tries to build/validate every object in the release - including our `ClusterPolicy` - against the API server's *current* CRDs, which don't exist yet on a first install (`resource mapping not found for kind "ClusterPolicy" ... ensure CRDs are installed first`). Confirmed live. Same two-phase shape as `ITL.Identity.Spire`'s `spire-crds` chart, for the same reason - just without a separate chart, since Kyverno ships its own CRDs as regular templates within the one chart.

```bash
cd itl.kyverno
helm dependency update

# 1. First install: our own policy disabled, so only Kyverno + its CRDs land
helm upgrade --install kyverno . -n kyverno --create-namespace \
  --set policies.spiffeHelperNonRoot.enabled=false

# 2. Wait for the four controllers to be Ready, then enable our policy
kubectl wait --for=condition=Ready pod -l app.kubernetes.io/instance=kyverno -n kyverno --timeout=120s --all
helm upgrade kyverno . -n kyverno --set policies.spiffeHelperNonRoot.enabled=true
```

A subsequent `helm upgrade` (once the CRDs already exist) does not need this split - a plain `helm upgrade kyverno . -n kyverno -f values.yaml` is sufficient from then on. One gotcha found live: `helm upgrade` without `-f`/`--set` silently keeps any `--set` flags from a *previous* invocation (not just the chart's own `values.yaml` defaults) - re-running step 2's `--set policies.spiffeHelperNonRoot.enabled=true` explicitly is what's required to turn it back on after step 1's `=false`, a bare `helm upgrade kyverno .` does not revert to the chart default.

## Verify

```bash
kubectl get pods -n kyverno
kubectl get clusterpolicy
kubectl describe clusterpolicy spiffe-helper-nonroot
```

A pod containing a `spiffe-helper` container, created *after* this chart is installed, should show the patched `securityContext` (`runAsUser`/`runAsGroup` from `values.yaml`'s `policies.spiffeHelperNonRoot.uid`/`gid`) without any change to the chart that created that pod:

```bash
kubectl get pod <pod> -o jsonpath='{.spec.initContainers[?(@.name=="spiffe-helper")].securityContext}'
```

## Verified live, and the two real bugs that surfaced doing it

Tested against two cases on the real cluster: a plain pod with no `spiffe-helper` container at all (must be admitted unchanged), and a pod with a `spiffe-helper` container carrying no `securityContext` (must come out patched to `runAsUser`/`runAsGroup` from `values.yaml`). Both pass as of revision 7. See [2.1](../2-policies/2.1-spiffe-helper-nonroot.md) for what actually went wrong getting there - in short:

1. **First version used a top-level precondition** (`length(request.object.spec.initContainers[?name=='spiffe-helper']) > 0`) instead of `mutate.foreach`. `spec.initContainers` is an optional field, absent entirely (not merely `null`) from the admission request JSON for most pods - JMESPath errored on that absent key, and with Kyverno's default `failurePolicy: Fail`, **this blocked admission of every pod cluster-wide that matched the rule's `match` block** (effectively most pods, since lacking `initContainers` is the common case) for as long as the policy was enabled. Confirmed live, twice, each time caught within roughly a minute and fixed by disabling the policy (`--set policies.spiffeHelperNonRoot.enabled=false`).
2. **Switching to `mutate.foreach` alone wasn't enough** - `foreach.list` evaluating an absent key threw the same class of error (`Unknown key "initContainers" in path`), for the same reason. Fixed with a JMESPath null-coalesce: `list: "request.object.spec.initContainers || []"`.
3. **`failurePolicy: Ignore` was added at the policy level regardless of whether the JMESPath was fixed correctly** - a deliberate, permanent decision, not a workaround removed once the real bug was found. A policy this generic (matches `kind: Pod` with no namespace/label scoping) should never be able to turn a logic bug in its own rules into a cluster-wide outage; `Ignore` means a future bug degrades to "this one mutation silently doesn't apply" instead.

Lesson for any future policy added to this repo: test against a pod **without** the field/container the policy is supposed to match, not just a pod with it - that's the case the write-up above actually broke on, twice.
