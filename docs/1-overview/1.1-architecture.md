# 1.1 Architecture

**Status: scaffolded, not yet deployed.**

## What this is

A thin wrapper around the upstream [`kyverno/kyverno`](https://kyverno.github.io/kyverno/) Helm chart (see `itl.kyverno/Chart.yaml`), the same pattern as `ITL.Identity.Spire` for SPIRE: upstream owns the manifests (admission controller, background controller, reports controller, cleanup controller, their RBAC and webhooks), this wrapper only overrides what's actually cluster-specific. `itl.kyverno/values.yaml` currently overrides exactly one thing (`admissionController.replicas: 1`, since this is a single lab-scale cluster) and adds this wrapper's own policies under its own `policies.*` key.

## Why Kyverno, and why as a cluster-wide tool rather than a per-app fix

The concrete trigger: `ITL.Openproject.fork` needed a non-root `securityContext` on the `spiffe-helper` sidecar container that SPIFFE workload identity (`ITL.Identity.Spire`) injects. Fixing it inside that one chart works, but the next chart that adopts SPIFFE workload identity hits the exact same bug and has to rediscover it from scratch - the fix doesn't travel with the pattern, only with that one app. A cluster-wide Kyverno policy that matches on container *name*, not on which Helm release or namespace created the pod, fixes it once for every current and future consumer - see [2.1](../2-policies/2.1-spiffe-helper-nonroot.md).

Kyverno specifically (over OPA Gatekeeper, the other mainstream option): policies are plain YAML (Kubernetes-native resource shape - `ClusterPolicy`, `match`/`mutate`/`validate`), not a separate language (Rego). `mutate` is a first-class, well-documented capability; Gatekeeper's mutation support exists but is less central to how the project is used in practice. For a cluster this size, with no existing Rego expertise anywhere in these repos, the lower-friction option wins.

## The three rule types, and which this repo uses so far

- **`mutate`**: changes a resource before it's persisted (what [2.1](../2-policies/2.1-spiffe-helper-nonroot.md) uses - patches a container's `securityContext`).
- **`validate`**: accepts or rejects a resource against a rule (not used yet - a candidate for later: enforcing Pod Security Standards beyond what the built-in PSA admission controller covers, blocking `:latest` image tags, requiring resource limits).
- **`generate`**: creates a companion resource automatically (not used yet - a candidate for later: auto-creating a default `NetworkPolicy` or `ResourceQuota` for every new namespace).

## Not a replacement for anything already in the cluster

This is new, additive infrastructure - it doesn't replace Kubernetes' own Pod Security Admission (PSA, label-based, built into the API server) or anything Cilium/Tetragon already enforce at the network/eBPF layer. It operates purely at the Kubernetes admission-API level, on resource shape, not network traffic or syscalls.
