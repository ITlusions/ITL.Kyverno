# 2.2 SPIFFE Helper injection

**Status: deployed and verified live** on the `itl` cluster, 2026-10-29.

## What this is

Annotation-driven SVID sidecar injection, reusable cluster-wide. Any pod template carrying the annotation below gets a full `spiffe-helper` setup added at admission time - the CSI volume, a certs volume, a config file, and the `spiffe-helper` container itself as a native sidecar - without that workload's own chart hand-rolling it the way `ITL.Openproject.fork` had to (see that repo's `docs/5-authentication/5.3-spiffe-mtls-postgres.md` for everything that took to get right by hand: native-sidecar ordering, the broken `exec`-based startupProbe, `-daemon-mode=false` hanging, the root/uid file-permission bug this repo's own `spiffe-helper-nonroot` policy, [2.1](2.1-spiffe-helper-nonroot.md), fixes separately). This is the generic version of that same work, offered to any future consumer as "add one annotation" instead of "patch your chart's templates".

```yaml
metadata:
  annotations:
    spiffe.itlusions.local/inject: "true"
```

On the **pod template** specifically (`spec.template.metadata.annotations` for a Deployment/Job, not the Deployment/Job's own top-level `metadata.annotations`) - Kyverno's `match` matches on the actual `Pod` object the API server is admitting, which only ever sees the pod template's annotations.

## Why no ConfigMap

`ITL.Openproject.fork`'s own `spiffe-helper-configmap.yaml` works because it's namespace-scoped - one chart, one release, one namespace, the ConfigMap and the pod that mounts it are created together. A cluster-wide injector can't make that assumption: it has no way to pre-create a ConfigMap in every namespace a matching pod might ever land in, and Kubernetes volumes can only reference a ConfigMap in the same namespace as the pod.

Matches `cofide/spiffe-enable`'s own approach, confirmed by reading its source during evaluation of that project (see [1.1 Architecture](../1-overview/1.1-architecture.md) and this session's earlier evaluation of it as an alternative to building this ourselves): the config content is a literal multi-line string, patched in as an env var on a small `busybox` init container (`spiffe-helper-config-writer`), which writes it to an `emptyDir` the `spiffe-helper` sidecar then reads from. Fully self-contained - nothing to pre-create per namespace, nothing that can drift out of sync with a ConfigMap maintained separately.

## What it deliberately does not do

**Does not mount anything into the workload's own application container(s).** This policy has no way to know which of a pod's *other* containers actually need `/certs` - mounting it into all of them unconditionally would be a bigger, riskier default than an injector should make on a consumer's behalf. The consuming chart still adds its own `volumeMounts` for `spiffe-workload-api` and `spire-certs` wherever it actually needs the files (the same shape as `ITL.Openproject.fork`'s `extraVolumeMounts` - both volumes are harmless to mount even in a container that never ends up reading from them).

**Does not touch SPIRE registration.** The injected sidecar will run and log `no identity issued` (`PermissionDenied`) forever if no `ClusterSPIFFEID` actually matches the pod - confirmed live in the test below. That's correct, expected behaviour, not a bug in this policy: registration is a separate concern, owned by whichever `ClusterSPIFFEID` the consuming workload's own chart defines (see `ITL.Identity.Spire`).

## Idempotency

The rule's precondition checks that no `initContainers` entry is already named `spiffe-helper` before patching - re-admission of an already-injected pod (e.g. after a node reschedule, if the API server ever re-runs admission on an existing object) is a no-op rather than stacking a second copy of everything. Same `foreach`-safe JMESPath null-coalesce as [2.1](2.1-spiffe-helper-nonroot.md): `request.object.spec.initContainers[].name || `[]``, not a bare field reference.

## Verified live

Tested against two cases in the `default` namespace: a plain pod with no annotation (confirmed unaffected - no `initContainers`, no extra volumes), and a pod with the annotation and no SPIFFE registration anywhere (confirmed: both initContainers and all three volumes were injected exactly as designed; the `spiffe-helper` sidecar started, read its config correctly, and logged the expected `no identity issued` since nothing registers that throwaway test pod with SPIRE - the correct failure mode at the registration boundary, not a defect in the injection itself).

## Configuration

```yaml
policies:
  spiffeHelperInject:
    enabled: true
    annotation: "spiffe.itlusions.local/inject"
    sidecarName: spiffe-helper
    uid: 1000
    gid: 1000
    spiffeHelperImage: "ghcr.io/spiffe/spiffe-helper:0.11.0"
    initHelperImage: "busybox:1.37"
```

`uid`/`gid` carries the same constraint as [2.1](2.1-spiffe-helper-nonroot.md): must match whatever uid the *consuming* application's own containers run as, for the files this sidecar writes to actually be usable.
