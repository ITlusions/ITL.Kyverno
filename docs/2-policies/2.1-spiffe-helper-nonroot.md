# 2.1 SPIFFE Helper non-root

**Status: deployed and verified live** on the `itl` cluster, 2026-10-29 - see [1.2 Deployment](../1-overview/1.2-deployment.md) for the two real bugs found getting here and how they were fixed (`mutate.foreach` instead of a top-level precondition, a JMESPath null-coalesce for the optional `initContainers` field, and `failurePolicy: Ignore` kept permanently as a blast-radius limit).

## The bug this fixes

`spiffe-helper` (the sidecar/init-container that materializes a SPIFFE SVID as `tls.crt`/`tls.key`/`ca.pem` files from the Workload API) defaults to running as root. It writes `tls.key` with mode `0600`, owned `root:root`. Any application container that runs as a non-root uid - which every chart in this cluster following the Bitnami-style convention does (`runAsUser: 1000`) - cannot read that file.

The failure mode this produces is easy to misdiagnose: the client library (in the one confirmed live case, Ruby's `pg` gem via ActiveRecord) does not raise a file-permission error. It silently skips a certificate it cannot read and connects without presenting one, so the actual error surfaces on the *server* side as `PG::ConnectionBad: ... requires a valid client certificate` or `SSL error: tlsv1 alert unknown ca` - which reads like a CA-trust or registration problem, not a file-permission one. See `ITL.Openproject.fork`'s `docs/5-authentication/5.3-spiffe-mtls-postgres.md` for the full incident this was found in.

This is not specific to that one app or that one chart - it reproduces for any workload that (a) uses SPIFFE workload identity via a `spiffe-helper` sidecar and (b) runs its application container as a non-root uid, which is most of this cluster's app charts.

## What the policy does

`itl.kyverno/templates/spiffe-helper-nonroot.yaml`, a `ClusterPolicy` with two `mutate.foreach` rules - one over `spec.initContainers`, one over `spec.containers`, since `spiffe-helper` can legitimately appear in either depending on the injection pattern (a native sidecar, `restartPolicy: Always` inside `initContainers` - what `ITL.Openproject.fork`'s own fork and the `cofide/spiffe-enable` injector both use - or a plain long-running container). Each rule:

1. Matches on `Pod` (no namespace/label scoping - deliberately cluster-wide).
2. Iterates the relevant container list with `foreach`, filtered by a precondition on `{{ element.name }}` equalling `spiffe-helper` - a no-op for every container that isn't one, in every pod that doesn't have one. The `initContainers` rule's list expression is `request.object.spec.initContainers || []`, not a bare field reference - see [1.2 Deployment](../1-overview/1.2-deployment.md) for why that `|| []` is load-bearing, not defensive-programming boilerplate.
3. Patches the matching container's `securityContext` to `runAsUser`/`runAsGroup` (from `values.yaml`, default `1000`), `runAsNonRoot: true`, drops all capabilities, disables privilege escalation, and sets the default seccomp profile - matching the hardened `securityContext` convention this cluster's other app containers already use, not inventing a new one.

**`failurePolicy: Ignore`** at the policy level, set deliberately and kept permanently: this policy matches every `Pod` in the cluster with no scoping, so a bug in its own logic must never be able to escalate into blocking pod admission cluster-wide. See [1.2 Deployment](../1-overview/1.2-deployment.md) for the incident that made this non-negotiable rather than a nice-to-have.

**Kyverno's own `{{ }}` templating (`{{ element.name }}`) is escaped past Helm's `{{ }}` templating** in the chart source using backtick raw-string literals (`{{` `` ` ``{{ element.name }}`` ` ``}}`), since both engines use the identical delimiter. Forgetting this escaping fails loudly (`helm lint`/`helm template` errors with `function "element" not defined`), unlike the JMESPath bugs below, which failed silently in the sense that they were syntactically valid Helm/YAML and only broke at Kyverno admission-request time.

## Configuration

```yaml
policies:
  spiffeHelperNonRoot:
    enabled: true
    uid: 1000
    gid: 1000
```

`uid`/`gid` must match whatever uid the *consuming* application's own containers run as - not a property of `spiffe-helper` itself. This cluster currently standardises on `1000` everywhere this matters, so a single cluster-wide value is sufficient; if a future consumer runs as a different uid, this policy as written cannot accommodate both at once (it has no per-namespace or per-label override) - would need a second rule or a label-driven lookup at that point, not a reason to avoid shipping the single-uid version now.

## Limits

- **Does not create the CSI volume, the certs volume, or the `spiffe-helper` container itself.** This policy only ever patches a `securityContext` on a container that something else already created - either a hand-rolled template (`ITL.Openproject.fork`'s pattern today) or an injector webhook (`cofide/spiffe-enable`, evaluated but not adopted - see that evaluation in this session's history for why). It is not an alternative to either; it is a cluster-wide correction layered on top of whichever one a consumer picks.
- **Not yet verified to coexist correctly with `cofide/spiffe-enable`** specifically, if that injector is ever adopted - that webhook and this Kyverno policy would both be mutating admission webhooks touching the same Pod object, and their relative ordering (which one the API server calls first) is not something this repo controls or has tested.
- **`failurePolicy: Ignore` is a deliberate trade-off, not a free safety net.** If the `mutate.foreach` rule silently fails to match for any reason (a future Kubernetes API change, a typo reintroduced later), nothing alerts - the pod is admitted unpatched, and the original root/uid-mismatch bug reproduces with no signal pointing back at this policy. `Ignore` was chosen anyway because the alternative (`Fail`) is what caused the cluster-wide admission outage documented in [1.2 Deployment](../1-overview/1.2-deployment.md) - a silent miss is strictly preferable to a cluster-wide block, for a policy this broadly scoped.
- **Only covers the uid/gid mismatch.** It does not address, and was never meant to address, the other `spiffe-helper` gotchas found integrating it into `ITL.Openproject.fork` (native-sidecar container ordering, the broken `exec`-based `startupProbe` on an image with no shell, `-daemon-mode=false` hanging instead of exiting) - those remain per-chart concerns, not admission-time-patchable ones.
